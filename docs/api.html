import type {Branded} from '@fuzdev/fuz_schema/schema.js';

Strict nominal typing. A plain value of the base type is not assignable to the branded type, so the only way to get one is through a schema or a cast. Good for values that must have been validated.

type Uuid = Branded<string, 'Uuid'>; const a: Uuid = 'abc'; // error! const b: Uuid = 'abc' as Uuid; // ok

null and undefined pass through unmarked: Branded<string | null, 'Uuid'> is the branded string or null, and a plain null is assignable to it.

Flavored
#

schema.ts view source

Flavored<TValue, TName>

type (TValue & Flavor<TName>) | (TValue & (Extract<TValue, null | undefined>))

import type {Flavored} from '@fuzdev/fuz_schema/schema.js';

Loose nominal typing. A plain value of the base type is assignable to the flavored type, so producing one needs no cast or parse, but two different flavors of the same base type are not assignable to each other. Good for values like ids and units, where mixing them up is the bug to prevent.

type Email = Flavored<string, 'Email'>; type Address = Flavored<string, 'Address'>; const email: Email = 'a@b.c'; // ok const address: Address = email; // error!

null and undefined pass through unmarked: Flavored<string | null, 'Email'> is the flavored string or null.

Of a type parameter whose constraint rules out null and undefined, as T extends string and T extends {} do, two flavors assign to each other. Generic code that keeps them apart flavors the constraint and intersects it with the parameter, which a plain T still assigns to:

// compiles: the two flavors of `T` mix const f = <T extends string>(x: Flavored<T, 'UserId'>): Flavored<T, 'PostId'> => x; // error! const g = <T extends string>( x: T & Flavored<string, 'UserId'> ): T & Flavored<string, 'PostId'> => x;

format_schema_type
#

introspect.ts view source

(schema: AnySchema): string import {format_schema_type} from '@fuzdev/fuz_schema/introspect.js';

Renders the type schema accepts as TypeScript-like text, for help output: Array<string> | null, {name: string; port?: number}, "a" | "b".

  • A with_default and a with_default_fn render as their schema, leaving the default to be shown apart, and an optional adds | undefined.
  • An entry is marked ? when a layer is an optional, a with_default, or a with_default_fn. A union with an optional option lets the key be missing too, and isn't looked into.
  • A pipe renders as its first schema, what it accepts.
  • A lazy renders as the schema its function returns, once, and one that returns a lazy as what that returns: a lazy inside that renders as ..., recursive or not. So a recursive schema shows one level of itself, whatever its functions build, short of a lazy that only returns a lazy, which a parse can't end either, and a lazy nested in another shows as ... though it would end.
  • A string literal is quoted as JSON, as the expected text of an issue has it, and a bigint ends in n.
  • A kind with no text of its own, an action or one defined outside the library, renders as its kind.

get_issue_value
#

schema.ts view source

(issue: SchemaIssue, input: unknown): { ok: true; value: unknown; } | { ok: false; } import {get_issue_value} from '@fuzdev/fuz_schema/schema.js';

Reads the value issue is about out of input, the value that was parsed, by following issue.path. It refuses where it would have to guess:

  • when the path leads through something that isn't an object or array
  • when what it finds is not of the type the issue received

Only own keys are read. A key that is missing reads as undefined, which is what the schema saw, so a missing required key is found with the value undefined. An inherited value is never returned.

The check is by type name, so it can't tell a value from another of the same type. Where an earlier step of a pipe replaced the value with one of its own type (a transform, or a container that applied a default or dropped a key) the issue is about the replacement, and what is returned is the input's value at that path.

Checks whether value has the shape of a schema: an object with a string kind, a def, and a run function.

The check is structural and stops there. It doesn't look at whether kind is one SchemaDefs describes or whether def is what that kind holds, so the narrowing is a claim about values this library built, not a validation of ones that came from elsewhere. Keys past the three are ignored.

The narrowed type is for reading a schema as data. A schema typed with its kind keeps its own type, while one typed as a bare Schema or AnySchema (as recursive schemas usually are) reads as SchemaNode, whose output type is unknown.

number
#

schema.ts view source

Schema<number, number, "number", undefined>

type Schema<number, number, "number", undefined>

import {number} from '@fuzdev/fuz_schema/schema.js';

Matches a finite number: rejects NaN and the infinities, with the issue any value that isn't a number gets.

A JSON text can carry an infinity as a number too large for a double, which JSON.parse reads 1e999 as, and JSON.stringify writes one back as null. An integer of any size is a finite number, see integer.

Only number is about which numbers: a literal or a one_of of an infinity still matches it, and a bound of min_value or max_value may be one.

As an object entry it hands schema the object and the key when schema takes them, so pipe(unknown, ...) fails a missing key and runs no action. The actions are handed neither.

As an object entry whose key is missing, a pipe that starts with an optional runs no action, and the key stays out of the output: object({a: pipe(optional(string), check(...))}) accepts {} whatever the check says, and a transform there writes no key. with_default and with_default_fn are what fill a missing key in. With the key there every action runs, on undefined too.

That is of an optional itself, and of a pipe that starts with such a pipe, as the entry itself or under a message. Under a nullable, a lazy, or a union its actions run on the undefined a missing key reads as, and so do a pipe's after a nullable, a lazy, or a union that reaches an optional.

Schema<TOutput, TInput, TKind, TDef> import type {Schema} from '@fuzdev/fuz_schema/schema.js';

A schema or action. run returns the output for value, or reports a failure with fail and returns anything.

All schemas share this exact shape so run call sites stay monomorphic; kind-specific data goes in def.

The object schemas call an entry's run with three more arguments, the object being read, the entry's key, and 1, so a schema that accepts undefined can tell a key that is missing from one that is there. nullable, lazy, union, pipe, and message pass the object and the key on to what they hold as the entry, and only message passes the third, which says that what it holds is the entry itself. Every other call gives the first two only, and a run that takes only those works as an entry.

union
#

schema.ts view source

<const T extends ReadonlyArray<AnySchema>>(options: T): Schema<ReturnType<T[number]["run"]>, InferInput<T[number]>, "union", T> import {union} from '@fuzdev/fuz_schema/schema.js';

Matches the first of options that accepts the value. On failure reports one issue, not the options' own.

As an object entry it hands every option the object and the key when any of them takes them. So a missing key matches only where an option lets its key be missing, as an optional does and an unknown doesn't, and with none it fails as any other value does, with the union's issue. The first option that matches is the union's, and a missing key it leaves undefined stays out: union([unknown, optional(string)]) accepts a missing key with the optional. When the option that matches fills a value in, as a with_default or a with_default_fn does, the key is optional and the undefined it reads as is for the options before to match: each of them that takes the object and the key is run again without them, and the first that matches is the union's. So union([pipe(unknown, ...), with_default(...)]) runs the pipe's steps on undefined in place of filling the default in, and union([unknown, with_default(...)]) leaves the key out. The make of a with_default_fn there is called, and what it returns dropped. An option run again runs twice in the parse, and a transform in it that the first run reached runs twice too, once more for each enclosing union that tries it again.

unknown
#

schema.ts view source

Schema<unknown, unknown, "unknown", undefined>

type Schema<unknown, unknown, "unknown", undefined>

import {unknown} from '@fuzdev/fuz_schema/schema.js';

Accepts anything.

As an object entry it needs its key: undefined at a key the object has, own or inherited, is accepted, and a key that is missing fails as a missing_key. Write optional(unknown) to let the key be missing.

It tells the two apart by the object and key the object schema hands it, which reach it as the entry itself and through flavor, brand, message, nullable, lazy, an option of a union, and the first schema of a pipe. Anywhere else it is told nothing of a key and accepts undefined: at the top level, as an array's item, as a record's value, and as a step of a pipe after the first. Under a union whose first option to match a missing key after it fills the key in, as a with_default does, the key is optional, and it accepts the undefined, see union.

with_default_fn

schema.ts view source

<T extends AnySchema>(schema: T, make: () => ReturnType<T["run"]>): Schema<ReturnType<T["run"]>, InferInput<T> | undefined, "with_default_fn", { ...; }> import {with_default_fn} from '@fuzdev/fuz_schema/schema.js';

Replaces undefined with what make returns, called with no arguments once for each value it fills in. As an object entry it makes the key optional in the input and required in the output, as with_default does.

What make returns is not validated, as with with_default, and as in Zod. It is for a default that must be new on every parse, as a mutable array or object must, or that is computed when it is filled in: with_default_fn(s.array(s.string), () => []).

As an object entry whose key is missing, a make that returns undefined leaves the key out, as with_default with a value of undefined does.
