benchmarks #

This page compares fuz_schemamaintainer's with Valibot, Zod, Zod compiled, Zod Mini, TypeBox, and ArkType: the bytes each ships, how long a parse takes, what a fresh process pays before its first parse, what stays in memory, and what the types cost the compiler. The maintainer of these benchmarks also maintains fuz_schema, so that library is marked wherever it is named, and how every number was measured is published with the numbers.

Every figure here is rendered from one results file, of one run. Beside a number is its ratio to the least in its row, or the most where higher is better, which reads 1.00×: 2.00× is twice as slow or twice as large. Hover a number to compare its row against that library instead. A ratio marked ≈ is inside what the two numbers range over, and one marked ~ has a time at the call floor: neither is a difference, and neither is colored. Where a number is level with the row's least, the least is marked ≈ too: the readings don't tell the two apart, and neither is the better. For two numbers of a row, what they range over is the two spreads together, the ± beside each. A geometric mean has a band in place of a spread, printed under it, from the mean of its rows' least readings to the mean of their most, and two means whose bands overlap are level. Each table says how its own figures are compared. A cell with no number says why it has none, and a number marked † is not ranked, nor is its row until a library is hovered. Bytes are in decimal units throughout: 1 kB is 1,000 bytes.

  • fuz_schema: A strict or identity parse of valid input returns the input itself, where Valibot and Zod return a copy.
  • Valibot: Its guard, is, runs the parser, which copies what it reads, and drops the copy.
  • Zod: Classic zod generates a parser for each object schema on its first parse where the environment allows eval. Its guard, z.validate, runs the parser where a schema has no compiled path, which copies what it reads, and drops the copy.
  • Zod compiled: Each root through z.compile, which generates its parser and its validator ahead of time. A root it hands back uncompiled has no timed figure. Each root through z.compile, which hands an invalid input to Zod's regular parser. A root it hands back uncompiled has no timed figure.
  • Zod Mini: Its objects never compile: zod/mini has no generated parser. Its guard, z.validate, runs the parser where a schema has no compiled path, which copies what it reads, and drops the copy.
  • TypeBox: Every row is a Check of its compiled validator, which stops at the first failure and builds no issues and no output.
  • ArkType: A parse that drops keys deep-clones its input before it runs.

Notes:

  • The guard sets aside a difference the parse rows carry: on a valid input a strict schema of this library returns the input itself, where Valibot and Zod return a copy of it, so a parse row there compares a check with a check and a copy.
  • TypeBox's rows are a Check of its compiled validator in every table: it stops at the first failure and builds no issues and no output.
  • ArkType's parse of a scenario that drops unknown keys deep-clones its input before it runs. Its guard, allows, clones nothing.
  • Compiled Zod is each scenario's root through z.compile, which generates a parser for a valid input and hands an invalid one to Zod's regular parser. A root it hands back uncompiled has no figure, and reads not compiled.
  • Every figure has a call in it: a function that does nothing took 3.87 ns to 3.94 ns through the loop the rows are timed in, across the processes. A time at or under 7.87 ns, twice the slowest of those, is at the call floor and mostly the call: its ratio is marked ~, and a scenario with such a time is in no mean.

How it was measured
#

Measured on laptop1 (AMD Ryzen 5 PRO 7530U with Radeon Graphics), Node v26.13.0, V8 14.6.202.34-node.40, on 2026-11-12, at commit e04d4b835a.

libraries

  • fuz_schema: @fuzdev/fuz_schema 0.6.0. This repository's source at the run's commit, not the published package of that version.
  • Valibot: valibot 1.5.0
  • Zod: zod 4.6.6
  • Zod compiled: zod 4.6.6. Zod with each root through z.compile, its ahead-of-time mode.
  • Zod Mini: zod 4.6.6. zod/mini.
  • TypeBox: typebox 1.3.36. The Check of its compiled validator.
  • ArkType: arktype 2.2.8

tools

  • rolldown 1.2.13
  • typescript 6.0.3

the machine

  • as the run started: load 0.08 0.81 1.23, CPUs at 1095 to 4392 MHz, performance governor, amd-pstate-epp driver, energy preference performance, boost on
  • as it ended: load 1.19 1.25 1.29, CPUs at 3504 to 4462 MHz, performance governor, amd-pstate-epp driver, energy preference performance, boost on
  • the run took 20.4 min
What each script was started with
  • npm run benchmark:bundle, which runs gro run src/benchmarks/bundle.ts, in 8 s
  • npm run benchmark:types, which runs gro run src/benchmarks/types.ts, in 66 s
  • npm run benchmark:allocations, which runs node --min-semi-space-size=64 --max-semi-space-size=64 src/benchmarks/allocations.ts, in 1.7 min
  • npm run benchmark:heap, which runs gro run src/benchmarks/run_heap.ts, in 15 s
  • npm run benchmark:coldstart, which runs gro run src/benchmarks/run_coldstart.ts, in 4.4 min
  • npm run benchmark, which runs node src/benchmarks/run.ts, in 3.9 min
  • npm run benchmark:survey, which runs node src/benchmarks/survey.ts, in 3.8 min
  • npm run benchmark:harvest, which runs node src/benchmarks/harvest.ts, in 4.3 min
  • npm run benchmark:wasm, which runs node src/benchmarks/wasm.ts, in 56 s
  • Bundle bytes and instantiations are exact. Bundle sizes and tsc's instantiations are the same on any machine for the same sources and tools. Allocation is exact for the code the engine is running, which a process settles and not always the same way, so a row repeats within about a percent, and a retained total to about a kilobyte: the tables compare each with that much either side.
  • Times are one machine's. They come from the machine named above, on one version of Node, with nothing pinned or isolated: what it was doing as the run started and ended is above. Compare the ratios between libraries before the absolute times, and read a gap against the spreads beside it: one inside them is not a finding, and one just outside is not much of one.
  • A process holds one library. What a library takes depends on what its process ran before, so no two share one, and a figure is what a library takes with the engine's attention to itself.
  • The scenarios are few and small, and all but one are synthetic. A test holds every library to the same answer on each scenario's inputs, so the rows compare the same question, not the same work: what each library builds on the way to its answer differs, as the notes above say.
  • It is V8 only. No other engine is measured.

The benchmarks' documentation has the method in full: what each script measures, how, and how far to trust each number. The results file this page renders is in the repository.
